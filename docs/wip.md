## Known bugs to fix

Found while writing controller tests to raise coverage; not yet fixed.

- **`APIGetWish` (`controllers/wish.go`) panics on a "wish not found" request instead of returning 400.** When `database.GetWishlistIDFromWish` returns `(nil, nil)` — i.e. no error, but no matching wishlist — the handler's `else if wishlistID == nil` branch logs `"Failed to find wishlist. Error: " + err.Error()`, calling `.Error()` on a `nil` error. That's a nil-pointer dereference: the request crashes the handler (gin's Recovery middleware would turn it into a bare 500 in production, masking the real cause) instead of cleanly returning the intended 400. Likely fix: drop `+ err.Error()` from that log line, or log a static message instead. Found via a test that had to be removed rather than kept, since it crashed the whole `go test ./controllers/...` run.
- **`ConvertWishToWishObject` (`controllers/wish.go`) panics on a wish with a dangling `WishlistID`.** It calls `_, wishlist, err := database.GetWishlistByWishlistID(wish.WishlistID)` and ignores the returned "found" bool, then later unconditionally dereferences `*wishlist.Claimable`. If the wishlist row doesn't exist, `database.GetWishlistByWishlistID` returns a zero-value `models.Wishlist{}` (found=false, err=nil), whose `Claimable` is a nil `*bool` — dereferencing it panics. Reached via `ConvertWishesToWishObjects`, so one wish with a dangling `wishlist_id` (e.g. from data corruption, or a future bug in a delete path) would crash the whole wishes listing for a user rather than just skipping that one wish. Likely fix: check the "found" bool and either skip the wish or return an error, same as the equivalent checks elsewhere in this file.
- **`RemoveSelfFromGroup` (`controllers/group.go`) is broken for everyone.** It builds an unbound `models.GroupMembership{}` and checks ownership using its zero-value `MemberID` (`uuid.Nil`) instead of the caller's own ID. GORM silently drops that zero-value field from the `Where` struct condition, so the ownership check degrades to "does an enabled group with this ID exist" — true for basically any group. The handler then always takes its "owners cannot remove themselves" branch, so **no one can currently leave a group** through this endpoint. Likely fix: check ownership against the caller's real `userID`.
- **`OIDCCallback` (`controllers/oidc.go`) never actually clears its state/nonce cookies.** The cleanup is `defer`red after `ctx.Redirect(...)`, but gin finalizes response headers at redirect time, so the deferred `SetCookie` calls run too late on every path (success or failure).
- **`DeleteWish` (`controllers/wish.go`)** returns `500` instead of `404`/`400` when the wish doesn't exist.
- **`GetWishlists`'s `?top=` filter (`controllers/wishlist.go`)** has an off-by-one and fails to truncate when the result count is exactly `top+1`.
- **`GetWishlists`'s `?group=` filter (`controllers/wishlist.go`)** returns `500` for a caller who isn't a member of the group, where the equivalent check elsewhere (`GetWishlist`, `DeleteWishlist`, ...) returns `400`.
- **`UpdateUser` (`controllers/user.go`) panics (nil-pointer dereference) when saving changes for any unverified account with SMTP enabled.** In the "send verification e-mail" branch (`config.ConfigFile.SMTPEnabled && !*user.Verified`), it does `*user.VerificationCode = verificationCode` — but `user` was just re-fetched from the DB via `database.GetAllUserInformation(userID)`, and `VerificationCode` is a `*string` that's nil unless a code was previously generated for that row. Any unverified user (e.g. one who registered but hasn't confirmed their e-mail yet) saving any profile change — even just their name — crashes the request. Likely fix: allocate the pointer (`user.VerificationCode = &verificationCode`) instead of dereferencing it. Found via a test that had to be removed rather than kept, since it crashed the whole `go test ./controllers/...` run — see the note left in `controllers/user_test.go` near `TestUpdateUserProfileImageFailure`.
- **`UpdateUser` (`controllers/user.go`) doesn't actually unverify an account after an e-mail change.** On an e-mail change it calls `database.SetUserVerification(userID, false)` directly against the DB, but never updates the in-memory `userOriginal.Verified` field to match. The very next step, `database.UpdateUserInDB(userOriginal)`, saves that whole (still-verified) struct back, silently reverting the unverify. Two consequences: (1) the account keeps `verified: true` despite the new e-mail address never being confirmed, and (2) the "send a new verification e-mail after an e-mail change" branch — gated on `!*user.Verified` — never fires even with SMTP enabled, so the user never gets a re-verification e-mail either. Likely fix: set `userOriginal.Verified` (or re-fetch) before the `UpdateUserInDB` save. Regression tests pinning the current behavior: `TestUpdateUserEmailChangeDoesNotActuallyUnverify`, `TestUpdateUserEmailChangeSMTPEnabledDoesNotSendVerification` in `controllers/user_test.go`.

## Known coverage gaps (intentional, for now)

- **`invite.go`'s "Failed to process invites" branches (`RegisterInvite`, `APIGetAllInvites`, `APIDeleteInvite`) are dead code, capping their coverage.** All three call `ConvertInvitesToInviteObjects`, which never returns a non-nil error — it treats a single bad row (e.g. a dangling `RecipientID`) by skipping it and continuing, not by failing the whole conversion. So the `if err != nil { ... "Failed to process invites." }` branch after each call can't be reached without changing that function's contract. Not a bug (the skip-and-continue behavior is intentional per `ConvertInvitesToInviteObjects`'s doc comment), just dead error-handling worth removing or wiring to something reachable if anyone revisits this file.
- **`group.go`'s `GetGroupObjects` has the same dead-code shape.** It calls `ConvertGroupsToGroupObjects`, which (like `ConvertInvitesToInviteObjects`) skips a single bad group and continues rather than ever returning a non-nil error, so `GetGroupObjects`'s `if err != nil { ... "Failed to convert groups to group objects." }` branch is unreachable. Same non-bug, same low-priority cleanup if anyone revisits this file.
- **`utilities/migrate.go`'s per-table foreign-key remapping (inside `ReplaceValues`'s `secondRun` switch, e.g. `groups` → `values[7]` is the owner column) is still untested.** `MigrateSQL`/`ReplaceValues`/`MigrateDBToV2`'s generic mechanics (two-pass scan, CREATE/INSERT detection, bigint→varchar(100) rewriting, numeric-ID→UUID substitution, the synthesized trailing `ALTER TABLE`, and the panic-on-missing-file behavior) now have real tests, using a table name that isn't one of the hardcoded special cases — that sidesteps the one part of this file that depends on knowing the exact old-schema column order for `groups`/`wishes`/`invites`/etc., which isn't documented anywhere and would be a guess. That specific per-table mapping remains untested; a real legacy-schema dump sample or someone who remembers the old schema would be needed to verify those column indices are actually right (they may not be — this was inherited, unverified legacy code). Low priority since it's not on any live code path for a current install.
