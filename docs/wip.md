## Known bugs (found while raising test coverage, not yet fixed)

The status-code tests below assert the *correct* codes and fail until the handlers are fixed.

- **A collaborator who edits a wishlist takes ownership of it.** `APIUpdateWishlist` sets `wishlistOriginal.OwnerID = UserID` (`controllers/wishlist.go:999`) even when the caller only passed the collaborator check at line 917. Relatedly, the unique-name check (line 955) looks at the caller's wishlists rather than the owner's.
- **Every wishlist edit regenerates the public link.** `APIUpdateWishlist` sets `PublicHash = uuid.New()` on every update (`controllers/wishlist.go:1006`), so even a description change breaks already-shared public links. Possibly intentional, but looks accidental.
- **Unclaiming a wish a second time reports failure.** `DeleteWishClaimByUserAndWish` (`database/wish.go:184-200`) has no `enabled` filter, so after claim → unclaim → claim it disables both the old and new claim rows, sees 2 rows affected instead of 1, and errors. The update has already run, so the claim is gone but the user gets a 400 "Failed to delete claim."
- **Registration can leave an invite reusable.** `RegisterUser` creates the user before marking the invite used (`controllers/user.go:169-175`); if the second step fails the user persists, the invite stays usable, and the caller gets a 400.
- **Group name/description are never trimmed.** `controllers/group.go:35-36` and `:870-871` trim the fields *before* the request values are copied in, so a mostly-whitespace name of 5+ characters passes the length check and surrounding whitespace is persisted.
- **`RegisterNewsPost`'s response filter is inverted relative to `GetNews`.** `GetNews` hides future-dated posts from non-admins (`Date.After(now) && !Admin`, `controllers/news.go:50`); `RegisterNewsPost` uses `Date.Before(now) && !Admin` (line 200) and doesn't sort. Low impact since the route is admin-only.
- **`ReplaceValues` can loop forever on malformed input.** In `utilities/migrate.go:209-232`, `sum` is never incremented, so the `for sum < 1000` guard does nothing; a row ending in an unterminated quoted string (e.g. `(1, 'abc);`) breaks out of the merge before `finishedLoop` is set and `MigrateSQL` hangs. The `index < len(values)+1` check on line 212 is also always true. Untested because the test would hang.
- **`RemoveFromWishlist`'s `!membershipFound` branch is dead.** `GetMembershipIDForGroupToWishlist` (`database/wishlist.go:368`) returns an error rather than `false` when nothing matches, so a membership that vanishes mid-request yields a 500 instead of the intended 400 (`controllers/wishlist.go:803-807`).
- **Status codes that break the handler error convention** (internal failures reported as 400, caller mistakes as 500). **These tests are deliberately failing** until the handlers are fixed: several lookups (`GetUserInformation`, `GetGroupMembershipByGroupIDAndMemberID`, `GetGroupInformation`, `GetInviteByID`, `GetGroupUsingGroupIDAndUserIDAsOwner`) don't distinguish "not found" from a real error, so the fix is to return a sentinel like `database.ErrWishlistNotFound` and branch 400 vs 500 on it. The failing tests: `TestJoinGroupCallerNotOwner`, `TestGetGroupMembersNotMember`, `TestGroupHandlersInjectedDatabaseFailures`, `TestDeleteInvite{NotFound,Used,Success}`, `TestGetUsersNotACollaboratorWishlistLookupFailure`, `TestGetUsersNotAMemberOfGroupMembershipLookupFailure`, `TestRegisterUserDatabaseFailures`, `TestUpdateUserDatabaseFailures`, `TestRemoveWishClaim_InjectedFailures`, `TestAPIGetWish_WishDisappearsMidRequest`, `TestDeleteWishlistUpdateDBFailure`, `TestDeleteWishlistGroupQueryListDBFailure`, `TestGetWishlistsGroupFilterListDBFailure`, `TestRemoveFromWishlistDBFailures`.
  - DB errors returned as 400: `controllers/wishlist.go` 251, 293, 371, 444, 853; `controllers/wish.go` 901; `controllers/group.go` 135-141, 405-408, 829-831, 911-916, 944-947; `controllers/user.go` 170, 329, 355, 587.
  - Caller mistakes returned as 500 (should be 400, or 404 for the vanished wish): non-owner member calling `JoinGroup` (`controllers/group.go`, the `GetGroupUsingGroupIDAndUserIDAsOwner` check); non-member calling `GetGroupMembers` (`controllers/group.go:810-811`); unknown or already-used invite in `APIDeleteInvite` (`controllers/invite.go:58-70`, which also returns 201 instead of 200 on success); a wish vanishing mid-request in `APIGetWish` (`controllers/wish.go:1243`).
  - `JoinGroup`'s user lookup and `APIAddWishlistsToGroup` already distinguish not-found (400) from other errors (500) and are the pattern to copy.
  - `controllers/wishlist.go:371` (`GetWishlist`) is the one site without a failing test: the same branch is also hit when the wishlist owner is disabled, where 400 is right (`TestGetWishlistOwnerDisabled`), so the fix needs `GetWishlistObject` to separate that case from a real DB error first.
- **Some older test helpers mutate `config.ConfigFile` without restoring it**, against the `t.Cleanup` rule: `setupCryptoTestKey` (`utilities/crypto_test.go`), `TestGenerateAndValidateTOTP` (`utilities/mfa_test.go`), `setupOAuthKey` (`auth/oauth_test.go`) and `setupMCPConfig` (`mcpserver/server_test.go`). (`controllers` tests now use the shared `restoreConfig` helper.) Nothing currently depends on the leak (the suite passes with `-shuffle=on`), but it can mask order-dependent tests.

## Known coverage gaps (intentional, for now)

- **`main()` itself (`main.go:35-130`, ~59 statements) is untested** because it calls `os.Exit` and `log.Fatal(router.Run(...))`. Covering it would mean extracting a `run() error`; not done since coverage is above target without it.
- **Error branches after `utilities.ValidateTextCharacters`/`ValidatePasswordFormat` are unreachable** (~25 sites across `controllers/`): both use constant regexes, so `regexp.Match` never errors. Dropping the `error` return from those validators would remove the dead branches.

- **`utilities/migrate.go`'s per-table foreign-key remapping (inside `ReplaceValues`'s `secondRun` switch, e.g. `groups` → `values[7]` is the owner column) still encodes an unverified legacy schema.** `MigrateSQL`/`ReplaceValues`/`MigrateDBToV2`'s generic mechanics (two-pass scan, CREATE/INSERT detection, bigint→varchar(100) rewriting, numeric-ID→UUID substitution, the synthesized trailing `ALTER TABLE`, and the panic-on-missing-file behavior) have real tests, using a table name that isn't one of the hardcoded special cases — that sidesteps the one part of this file that depends on knowing the exact old-schema column order for `groups`/`wishes`/`invites`/etc., which isn't documented anywhere and would be a guess. The column indices themselves are still unverified (this was inherited legacy code) and a real legacy-schema dump sample or someone who remembers the old schema would be needed to confirm they're actually right — `TestMigrateSQLColumnMappingOutOfRange` in `migrate_test.go` only proves the *mismatch* is now caught. As a defensive measure, `ReplaceValues` now runs each lookup through `mapColumn`, which bounds-checks the index against the row's actual column count and returns a clear error (surfaced by `MigrateSQL`, and by extension panicking `MigrateDBToV2`, same as its other failure modes) instead of either panicking with a raw out-of-range index or silently substituting the wrong column. Low priority since it's not on any live code path for a current install.

## Planned features

- **Orphaned image cleanup on `/admin`.** Deleting a wish, wishlist or user now removes its image files, but files left behind by deletions made before that change are still on disk. Plan: a section on the admin page (`web/html/admin.html` / `web/js/admin.js`) with two admin-only endpoints under `/api/admin`:
  - A read-only scan listing orphaned files and their total size. That means any `images/wishes/<id>{,_thumbnail}.jpg` whose wish doesn't exist, is disabled, or is on a disabled wishlist, and any `images/profiles/<id>{,_thumbnail}.jpg` whose user doesn't exist or is disabled. Stray `.upload-*.jpg` temp files from interrupted writes count too.
  - A delete action the admin confirms explicitly, which removes exactly what the scan found.

  Keep the scan and the delete as separate steps, since the delete removes user files for good. The filesystem walk belongs in `controllers/image.go`, and the "which of these IDs are still live" lookups in `database/`, which keeps the layering rule.
